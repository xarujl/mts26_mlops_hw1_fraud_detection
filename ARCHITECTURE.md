# Архитектура проекта

Streamlit отправляет транзакции в Kafka, ML-сервис обрабатывает их и публикует результаты, отдельный сервис сохраняет результаты в PostgreSQL, а Streamlit показывает агрегаты из базы.

```text
                          ┌─────────────────────┐
                          │      interface      │
                          │ Streamlit: отправка │
                          │ и просмотр отчёта   │
                          └───────┬───────▲─────┘
                                  │       │ читает отчёт
                         пишет    │       │
                                  ▼       │
┌──────────────┐  transactions  ┌──────────────┐  scoring  ┌──────────────┐
│    Kafka     │ ─────────────► │fraud_detector│ ────────► │    Kafka     │
│              │                │ preprocess → │           │              │
│              │                │score →publish│           │              │
└──────────────┘                └──────────────┘           └──────┬───────┘
                                                                    │ читает
                                                                    ▼
                                                            ┌──────────────┐
                                                            │  db_writer   │
                                                            └──────┬───────┘
                                                                   │ пишет
                                                                   ▼
                                                            ┌──────────────┐
                                                            │ PostgreSQL   │
                                                            └──────────────┘

         train (одноразовый запуск) ──► сохраняет модель в общий volume
                                            │
                                            ▼
                                      fraud_detector
```

## За что отвечает каждый контейнер

| Сервис | Задача |
| --- | --- |
| `interface` | Загрузка CSV, публикация транзакций, запрос отчёта из PostgreSQL |
| `kafka` и `zookeeper` | Передача сообщений между сервисами |
| `kafka-setup` | Создание топиков при старте окружения |
| `train` | Обучение модели на обучающих данных и сохранение артефакта |
| `fraud_detector` | Получение транзакции, препроцессинг, CPU-инференс, публикация результата |
| `db_writer` | Чтение результатов из Kafka и запись в PostgreSQL |
| `postgres` | Хранение результатов скоринга |
| `kafka-ui` | Визуальный просмотр топиков и сообщений |

## Поток данных

1. Пользователь загружает CSV в `interface`.
2. `interface` отправляет каждую строку JSON-сообщением в топик `transactions`.
3. `fraud_detector` читает сообщение, вызывает препроцессинг и модель, затем отправляет результат в топик `scoring`.
4. Результат содержит три поля: `transaction_id`, `score`, `fraud_flag`.
5. `db_writer` читает `scoring` и сохраняет три поля в PostgreSQL.
6. По нажатию кнопки интерфейс запрашивает из PostgreSQL последние 10 мошеннических транзакций и последние 100 скоров для гистограммы.

## Структура файлов

```text
.
├── docker-compose.yaml
├── interface/
│   ├── Dockerfile
│   └── app.py                  # отправка в Kafka + запрос отчёта из БД
├── fraud_detector/
│   ├── Dockerfile
│   ├── app/                    # запуск consumer/producer
│   ├── src/
│   │   ├── preprocessing.py    # преобразование одной транзакции
│   │   └── scorer.py           # загрузка модели и получение score
│   ├── train.py                # обучение и сохранение модели
│   ├── models/                 # артефакт модели (лучше общий volume)
│   └── train_data/
├── db_writer/
│   ├── Dockerfile
│   └── app.py                  # consumer scoring → INSERT в PostgreSQL
└── ARCHITECTURE.md
```

`app.py` связывает шаги, `preprocessing.py` преобразует данные, `scorer.py` отвечает за модель. Обучение не смешано с обработчиком Kafka.

## Docker Compose

Все контейнеры подключены к одной внутренней сети `ml-scorer`. Внутри Compose сервисы обращаются друг к другу по имени сервиса и внутреннему порту:

- Kafka: `kafka:9092`
- PostgreSQL: `postgres:5432`
- интерфейс доступен с компьютера на `localhost:8501`
- Kafka UI — `localhost:8080`

Порты PostgreSQL наружу не требуются: к базе обращаются `interface` и `db_writer` из Docker-сети. Настройки подключения (хост, имя базы, пользователь, пароль) передаются контейнерам через переменные окружения. Значения задаются в Compose.

Для PostgreSQL нужен именованный volume, чтобы данные сохранялись после пересоздания контейнера. Для модели обучения нужен отдельный общий volume, если `train` и `fraud_detector` должны видеть один и тот же артефакт. Сам volume хранит файлы, но не является сервисом.

На лекции был вопрос для чего написано в `depends_on` kafka и kafka-setup, хотя kafka-setup зависит от kafka. \
Так вот `depends_on` задает только порядок запуска, но сам по себе не гарантирует готовность Kafka или PostgreSQL принимать соединения. Там, где это важно, сервис должен повторять подключение до успеха либо использовать healthcheck и условие готовности. Прописаны дополнительные condition.

## Обучение и CPU-инференс

Команда обучения читает данные из `train_data`, создаёт модель и сохраняет её в `models`. Обработчик при старте загружает этот файл и использует его для предсказаний. Модель может быть заранее обучена и сохранена, а `train` запускаться отдельно, когда нужно потренироваться в процессе обучения.

## Интерфейс

Кнопка «Посмотреть результаты» выполняет два простых запроса:

1. Последние 10 записей, где `fraud_flag = 1`, в порядке убывания времени сохранения.
2. До 100 последних `score`; по ним строится гистограмма.

Для витрины достаточно одной таблицы, например `transaction_scores`: идентификатор транзакции, score, fraud_flag и время записи. `transaction_id` удобно сделать уникальным, чтобы повторное сообщение не создавало дубликат (вставка может обновлять существующую запись или игнорировать повтор).
